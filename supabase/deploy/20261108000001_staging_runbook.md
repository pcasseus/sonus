# 20261108000001 permanent deletion: staging runbook

Not deployed. Production needs the user's separate authorisation.

1. Throwaway database with every migration applied (as for
   20261026000001: a disposable `supabase/postgres` container with fake
   users). Never production.
2. Apply `migrations/20261108000001_permanent_deletion.sql` twice (it is
   idempotent).
3. Run `tests/permanent_deletion.sql`: every block prints PASS and rolls
   back.
4. Run `deploy/20261108000001_verify.sql`: the probe returns
   `{permanent_deletion_v1}`, six triggers exist, the kind check lists
   `library_deletion`.
5. Compatibility: a Sonus 1.0/1.1 client keeps working. It never sends the
   new kind or deletes history records; mutable archive kinds keep their
   rules. The only new refusal for old clients is reviving a library
   tombstone, which the client never does on its conditional paths.
6. Rollback: `deploy/20261108000001_rollback.sql` (drops the guards and the
   probe; keeps every row).

Until this is deployed, Sonus keeps permanent deletion unavailable on any
device linked to cloud sync (the probe fails), so nothing is deleted
locally that the cloud would later return.

## Verified end to end on an isolated local Supabase stack, 2026-11-08

A full Supabase CLI stack (v2.121.0; Postgres 17, GoTrue, Storage, PostgREST) in its own folder, as project `sonus_pd_staging` on ports 55420–55429. It was never linked to any project, and only synthetic users and records were used. Production and the `sonus_next` local stack were not touched.

**SQL tests:**
- All 18 migrations applied on a fresh start and again after `supabase db reset`.
- 20261108000001 applied twice (idempotent).
- Rollback, then forward again: clean, and the probe and the 6 triggers return each time.
- With real authentication, the receipt tests now pass. When the runner wraps them in a transaction, as their headers ask:
  - `artist_create_with_receipt` 12 PASS;
  - `artist_update_with_receipt` 17;
  - `artist_delete_with_receipt` 16;
  - `artist_write_receipt_constraint` 7.
- All other tests pass, except `artist_write_security_contract`, which is expected to fail until the receipt cutover.
- `tests/permanent_deletion_roles.sql` now creates its fake user inside the transaction, so it can run again on the same database.

**The app against the server**: the harness in `test/integration/staging/`, using the app's own sync stack (`SyncComposition`).
- **Server:**
  - S3: the signed-in user can call the probe. Deleted history can't be revived or refilled (42501, or 23514 for content on a deleted record). Deletion records can't be changed.
  - S4: a second user can neither see nor change the first user's library, archive or deletion records, nor forge one.
  - S5: anonymous callers are refused.
  - S6: removable kinds still work as before.
  - S7: a deleted song can't be revived, not even with the service role.
- **App:**
  - C1–C3: song, release and artist deletion, including confirmed shared recordings and kept collaborations. The cloud ends with tombstoned library rows, emptied history and Moment tombstones, and one deletion record per operation.
  - C4: charts are rebuilt without gaps, and no new Moments.
  - C5: another device applies the deletion and sends nothing of its own.
  - C6: an offline device's stale edit and play don't come back.
  - C7: a stale cloud write is ignored.
  - C8: a new device never sees the deleted song.
  - C9: restoring an older backup changes nothing in the cloud.
  - C10: a lost response is retried, with no duplicates.
  - C11: interrupted operations complete after a restart.
  - C12: a duplicate merge propagates.
  - C13: a deletion waits for its dependency, then applies.
  - C14: run with this migration rolled back. Deletion is blocked and nothing changes.
  - C15: the other user sees nothing.
- **Old clients:** the released App Update 1.1 code (4f7a36d), run against this server:
  - it syncs without error, and never revives anything in the cloud;
  - a fresh 1.1 install never receives the deleted song;
  - if a 1.1 device edits a song that was deleted elsewhere, that edit stays as a sync conflict on that device until it is updated;
  - a play it records later of a deleted song is removed from the cloud by the next 1.2 device that syncs.
- **Guard:** the harness refuses any target but `http://127.0.0.1:55421` with local demo keys and the server-side staging marker. It also refuses if the app configuration is loaded. Each refusal was checked live.

**Still required:** production deployment, which needs separate authorisation.
