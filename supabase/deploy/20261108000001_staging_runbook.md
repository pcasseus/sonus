# 20261108000001 permanent deletion: staging runbook

Not deployed. Production needs the user's separate authorisation.

1. Throwaway database with every migration applied (as for
   20261026000001: a disposable `supabase/postgres` container with fake
   users). Never production.
2. Apply `migrations/20261108000001_permanent_deletion.sql` twice (it is
   idempotent).
3. Run `tests/permanent_deletion.sql`: every block prints PASS and rolls
   back.
4. Run `deploy/20261108000001_verify.sql`: the probe returns
   `{permanent_deletion_v1}`, six triggers exist, the kind check lists
   `library_deletion`.
5. Compatibility: a Sonus 1.0/1.1 client keeps working. It never sends the
   new kind or deletes history records; mutable archive kinds keep their
   rules. The only new refusal for old clients is reviving a library
   tombstone, which the client never does on its conditional paths.
6. Rollback: `deploy/20261108000001_rollback.sql` (drops the guards and the
   probe; keeps every row).

Until this is deployed, Sonus keeps permanent deletion unavailable on any
device linked to cloud sync (the probe fails), so nothing is deleted
locally that the cloud would later return.
