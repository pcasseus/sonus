# Migration 20261026000001 — staging runbook

The change adds one new table, `public.sonus_archive_records`, with its own row-level security, grants and the two existing trigger functions. It is purely additive:
- no existing table, row, policy, grant or function changes;
- the app never deletes from it (no delete grant); a removal is recorded as `is_deleted`, keeping the content.

It holds what the library tables do not: playlists and their order, listening sessions with their qualified plays, lyrics, artwork crop positions, soundtrack classifications, collaborator assignments, and all-time Moments.

Apply `20261025000001` first (its own runbook). Both can go in one push, but one at a time is easier to verify.

## Already verified (local disposable Supabase Postgres)

Image `supabase/postgres:15.8.1.060` in a throwaway Docker container on localhost, with fake users and data.
- All 16 earlier migrations applied, plus 25 songs written the way an older app writes them; every song row and every policy snapshotted.
- **Preview:** inside a rolled-back transaction the table exists; afterwards it does not.
- **Apply twice:** the second run is a no-op (3 policies, 2 triggers, nothing duplicated).
- **Structure:** primary key `(user_id, library_id, kind, record_key)`, the cursor index, checks on kind, key length, library id, payload (an object, at most 1 MB) and revision.
- **Nothing else changed:** 19 policies before and after outside the new table, 0 changed; 0 song rows changed.
- **Owner:** insert gives revision 1; re-sending the insert with `on conflict do nothing` inserts 0 rows; an update at revision 1 gives revision 2; a stale update at revision 1 changes 0 rows.
- **Isolation:** a second user sees 0 rows, updates 0 rows, and cannot insert into the owner's account (RLS error). Deleting is refused (permission denied). `anon` is refused.
- **Bad rows:** an unknown kind, a non-object payload and an empty key are refused.
- **Rollback preview:** the table is renamed away, songs are untouched, and after the rollback of the preview the archive row is still there.

The app side is covered by tests: two devices on real SQLite, a loopback gateway, the first-link protection and the Settings choice.

## Staging procedure (your Supabase access; never paste tokens or passwords into chat)

### 1. Authenticate on your machine only

Run `supabase login`. It opens a browser and stores the token in the OS keychain. Never put tokens in commands, files or chat.

### 2. Verify the target before linking

Run `supabase projects list` and confirm the staging project's **name** and **reference ID** from the Supabase dashboard (Project Settings → General). Write down the production reference too, so you can check you are not on it.

Then link: `supabase link --project-ref <staging-ref>`. Enter the database password at the prompt.

Before **every** later command, confirm the linked project:

```
cat supabase/.temp/project-ref
```

It must print the staging reference and not the production one. If it doesn't, stop.

### 3. Preflight

- Run `supabase migration list`. Remote must show every migration up to `20261025000001` applied (or that one pending, if you push both), and `20261026000001` pending. Anything else pending that you don't recognise: stop.
- In the dashboard SQL editor (staging), run `20261026000001_verify.sql` and save the output. Sections 1–5 and 7–8 fail or are empty, because the table doesn't exist yet. Sections 6 and 7 (library counts) are your "before" record.
- Confirm that no one is using the staging project for anything else during the change.

### 4. Back up staging before changing it

Docker must be running; the CLI uses it for `pg_dump`. Keep the files **outside the repository** and never commit them, because they contain account data.

```
supabase db dump --linked -f <backup-dir>/staging_schema_before.sql
supabase db dump --linked --role-only -f <backup-dir>/staging_roles_before.sql
supabase db dump --linked --data-only -f <backup-dir>/staging_data_before.sql
```

Check that all three files are non-empty and that the schema file contains `create table "public"."songs"`. If the plan includes point-in-time recovery or daily backups, note the latest backup time in the dashboard (Database → Backups) as a second safety net.

### 5. Dry-run preview

Run `supabase db push --dry-run`. It must list exactly the expected migration (or both): `20261026000001_cloud_archive_records.sql`.

### 6. Apply

Run `cat supabase/.temp/project-ref` once more, then `supabase db push`.

### 7. Verify

Run `20261026000001_verify.sql` again. Expected:
1. 11 columns, with `record_id` generated;
2. the primary key and 6 other constraints, and both indexes;
3. RLS on and the three own-row policies (select, insert, update), with no delete policy;
4. `authenticated` with `INSERT, SELECT, UPDATE`, and no `anon` row;
5. both triggers;
6. every other policy identical to step 3;
7. library counts identical to step 3, and the archive at 0;
8. empty until an app syncs; then `duplicate_keys` must stay 0.

### 8. Check with the app

Use a staging build, two **test** accounts and disposable devices or emulators.
- **Device A** (test account 1): create a playlist with three songs in a set order, play a song to a qualified stream, edit lyrics, crop an album cover, mark a soundtrack, group a collaborator. Sync. Section 8 shows each kind.
- **Device B** (fresh install, same account): sign in. Settings shows "Waiting for your choice", and nothing has moved. Choose **Bring it to this device**, then sync until "Pending 0". The library arrives first, then the playlist (same order), stream history, lyrics, crop, classification and grouping.
- **Device B with test account 2:** must see nothing from account 1, and account 1's rows in section 8 stay the same.
- **Remove the playlist on A** and sync: section 8 counts it under `removed`. B still has the playlist.

### 9. Production

Same steps, linked to production, only after you approve. Back up first (step 4), and verify the target reference twice.

## Recovery plan

**App side:** nothing to do. An app checks whether the table exists. Without it, the app skips the archive and syncs the library as before. Every device keeps its playlists, history, lyrics, crops, organization and Moments locally either way.

**Database side:**
- Run `20261026000001_rollback.sql` and preview it first inside `begin … rollback`. It **renames** the table to `sonus_archive_records_rolled_back` and closes it to the app. Nothing is deleted.
- Then run `supabase migration repair 20261026000001 --status reverted`.
- To bring the archive back, use the rename-back steps at the end of the rollback file.

**What a rollback can lose:** nothing in the cloud; the rows are kept under the new name. While the archive is off, new playlists and history stay on each device and upload when it returns.

**Never:**
- run a remote `db reset`;
- drop the table;
- delete or edit archive rows by hand;
- run any of this against production without explicit approval.
