# Migration 20261025000001 — staging runbook

The change adds two nullable `jsonb` columns to `public.songs`, `edition_memberships` and `artist_credits`. Each has a check that it is an array. Nothing else changes:
- no data is rewritten;
- no policy or grant changes;
- no other table is touched.

## Already verified (local disposable Supabase Postgres)

The dry run used `supabase/postgres:15.8.1.060` in Docker, bound to localhost, with throwaway data.

**Before the migration:**
- all 15 earlier migrations applied;
- 25 songs, 2 editions and 2 artists written the way an older app writes them;
- every row, policy and count snapshotted.

**Preview:** the migration ran inside a transaction that was rolled back. Nothing changed.

**After applying:**
- the columns are `jsonb`, nullable, with no default, and both checks are present;
- row counts are unchanged, every pre-existing column of every song is byte-identical, and all 25 legacy rows hold NULL;
- policies in `public` and `storage` are unchanged: 0 added, 0 changed, 0 removed.

**RLS:**
- the owner can write the new columns (1 row);
- a second user reads 0 songs and updates 0 rows, and the owner's data stays intact.

**Compatibility:**
- an older app's update of other columns keeps memberships and credits, and `server_revision` rises by exactly 1;
- re-sending an insert (`on conflict (id) do nothing`) inserts 0 rows, so the permanent ID stays unique.

**Tests and recovery:**
- `supabase/tests/song_memberships_and_credits.sql` passes;
- the migration is idempotent: re-running it is a no-op, and applying it fresh adds both checks;
- a rollback preview inside a transaction removes only the two columns and keeps all 25 songs.

The local image lacks `storage.buckets.public`, which the hosted Storage service provides. It was added for the dry run only.

## Staging procedure (needs your Supabase access; never paste tokens into chat)

1. **Authenticate on your machine only.** Run `supabase login`; it opens a browser and stores the token in the OS keychain. Never put tokens in commands, files or chat.

2. **Link the staging project** (not production): `supabase link --project-ref <staging-ref>`. Enter the database password at the prompt.

3. **Record the state before:**
   - `supabase migration list` should show every migration up to `20261017000006` applied, and `20261025000001` pending;
   - run `20261025000001_verify.sql` and save its output. Sections 1, 2 and 5 are expected to fail or be empty, because the columns don't exist yet.

4. **Dry-run preview:** `supabase db push --dry-run`. It should list exactly one migration, `20261025000001_song_memberships_and_credits.sql`.

5. **Apply:** `supabase db push`.

6. **Verify:** run `20261025000001_verify.sql` again. You should see:
   - both columns, nullable, with no default;
   - both checks;
   - RLS on, and policies identical to step 3;
   - row counts identical to step 3;
   - every song with NULL memberships and credits;
   - no duplicate IDs.

7. **Check with the app** (a staging build, two test accounts, two disposable devices):
   - sign in on device A with a test account and create a Deluxe edition that inherits Standard, then sync;
   - on device B, a fresh install signed into the same test account, sync: the Deluxe listing and both credits should appear;
   - sign in on device B with the second test account: it must see nothing from the first.

8. **Production** follows the same steps, linked to production, only after you approve.

## Recovery plan

- **App side:** nothing to do. Apps check whether the columns exist and simply stop sending them if they are removed.

- **Database side:** run `20261025000001_rollback.sql`, then `supabase migration repair 20261025000001 --status reverted`. Preview it first inside `begin … rollback`.

- **What a rollback can lose:** only memberships and credits written since deployment. Devices keep them locally, and the next change to a song re-uploads them once the columns are back.

- **Never** run a remote `db reset`, and never drop tables or edit rows by hand.
